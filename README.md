# Project Lumen

Project Lumen 是一款使用 Godot 开发的第一人称、知识驱动探索解谜游戏原型。玩家在一座废弃研究设施中观察异常、尝试实验，并逐步修正自己对空间与世界规则的理解。项目的目标不是让玩家按提示完成谜题，而是让“我终于弄明白了”成为推进探索的动力。

> **项目状态：**已完成可运行的开场体验、多个独立技术原型及其自动化检查；核心空间谜题的玩家理解效果仍待不知情玩家测试。项目尚未制作成完整游戏。

## 核心设计理念

**知识即进展。** 玩家通过观察、回头验证、改变观察条件等行为建立假设，而不是依靠钥匙、任务清单或直接给出答案的说明。最初合理的解释可能只覆盖一部分事实；后续证据应让玩家主动重新理解此前到过的地方。

因此，关键发现优先依靠可比较的物理证据：物体留下的维修痕迹、固定设施与可移动结构的关系、真实视线及空间纵深。文档可以补充人物与设施的历史，但不能替玩家完成推理。设计重点是控制信息出现的时机，同时让错误认知也有充分理由。

这是我的个人项目。我负责游戏方向、谜题规则与实验设计、空间和关卡灰盒、环境叙事结构、Godot 原型推进、玩家验证方案，以及设计文档的整理和版本边界管理。代码与文档制作使用了 AI 辅助；设计目标、任务约束、原型评估和取舍由我主导。

## 核心原型

### 1. 量子状态持久化

这个独立原型要区分两个容易混淆的解释：物体移动后保留**当前状态**，还是回到旧位置时恢复**过去的状态**。玩家可改变移动模块上附着的控制杆，再观察它返回原位置后的状态；固定接口与模块自身的状态被有意分开。场景和自动化检查已验证这一区别在技术上成立，玩家能否自然注意并预测它仍待测试。[验证记录](docs/world/STATE_PERSISTENCE_PROTOTYPE_VALIDATION.md)

### 2. 观察与摄像系统

项目首先用玩家视线与稳定光束测试“观察会约束异常物体”的规则；摄像原型进一步检验普通监控设备能否作为同类观察源，而不是一个伪装成摄像头的开关。原型保持摄像头通电，只改变镜头到物体之间的实际视线，以比较物体的行为。摄像观察、遮挡及玩家视线的技术测试已通过；玩家是否会自己得出这一解释尚未验证。[验证记录](docs/world/PROJECT_LUMEN_CAMERA_OBSERVATION_VALIDATION.md)

### 3. 三设施共存验证原型

这个灰盒原型关注空间谜题的核心风险：玩家多次到访相似场所后，能否通过建筑细节、固定参照物和最终的直接观察，重新判断这些地方之间的关系。项目制作了先后造访的认知测试流程，以及两个可步行抵达的观察视点；几何、视线与路线的自动化检查已通过。同时建立了盲测流程和分析框架，用于未来检验玩家是否真的改变了理解，**目前不能声称谜题已被玩家读懂**。[几何验证](docs/world/TRIPLE_COEXISTENCE_GREYBOX_VALIDATION.md) · [认知原型验证](docs/world/TRIPLE_COEXISTENCE_COGNITIVE_PROTOTYPE_VALIDATION.md)

## 开发流程

**设计假设 → 灰盒原型 → 自动化技术测试 → 不知情玩家测试方案 → 根据证据迭代。**

每个原型只回答一个尽量明确的问题。例如，技术测试可以确认三个空间同时存在、视线没有穿墙、玩家能够走到观察点；它不能证明玩家认出了这些空间，更不能证明认知反转带来了预期情绪。项目将技术可行性与玩家理解分开记录，以避免把“能运行”误写成“设计有效”。

## 技术与工具

- **Godot Engine 4.7.2、GDScript：**第一人称场景、交互与独立灰盒原型。
- **Git、Markdown：**版本管理、设计规则、验证记录与测试材料。
- **AI 辅助开发：**协助实现原型、生成或检查代码、整理验证文档；不替代设计判断或真实玩家测试。

主场景从开场的「苏醒室」进入；空间谜题的独立测试场景需要分别运行，不等同于一条已完成的正式游戏流程。

## 当前项目状态

**已完成：**知识驱动探索的设计框架、可运行开场、多个独立技术原型、相关自动化验证，以及设计文档和盲测方案。

**尚未完成：**完整游戏内容与商业化制作、正式的不知情玩家理解验证，以及最终空间谜题在正式世界中的完整整合。现有结论以技术验证为主，玩家能否自然发现并运用这些规则仍是开放问题。

## 项目展示重点

Project Lumen 展示的是一套从**系统规则、玩家心理、空间证据**出发的解谜设计方法：先提出玩家可能怎样理解世界，再制作最小原型寻找反证，最后用技术检查与未来的玩家测试分别检验实现和体验。项目目前仍处于原型与验证阶段，这些尚未得到答案的问题也是下一步迭代的依据。
